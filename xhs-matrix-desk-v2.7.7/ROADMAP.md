# 小红书矩阵工作台 · 产品路线图

> 产品方向：将可运行的桌面工具逐步整理成便于维护的账号运营工作台。路线图描述规划，不代表全部功能已完成。
> 逐渐升级成"账号管理 + 内容矩阵 + 客户线索 + 销售跟进 + 数据分析"的小红书运营工作台。
>
> 总原则：先把"能用"变成"稳定可长期跑"，再把"人工操作工具"升级成"半自动运营工作台"。
> 不要每想到一个功能就直接往 webapp.py 里加代码——下一阶段核心是
> 模块边界、任务调度、状态管理、异常恢复。

## v2.8 · 任务中心 + 账号状态 + 线索 CRM + 选择器维护

1. **账号 Actor 架构强化**：所有浏览器操作封装成命令
   （publish / open_message / scan_contact / close …），外部线程禁止直接拿
   page/context。新增功能走命令注册，不再产生跨线程问题。
2. **SweepMonitor 后台巡检系统化**：6 分片保留；优化调度——轮询间隔动态调整、
   登录失效自动降级、连续失败冷却、人工浏览器使用中跳过、多账号错峰。
3. **账号状态中心**：在线 / Cookie 失效 / 需要验证 / 人工浏览器使用中 /
   后台巡检中 / 发布中 / 最近成功时间 / 最近错误。20～100 号不用逐个点进去看。
4. **发布任务系统**：一次批量发布 = 总任务 + 每账号子任务。
   能看到"17 成功、2 登录失效、1 页面异常"，只重试失败账号。
   注意：goto/加载/元素等待可重试；**真正的"点击发布"动作不盲目自动重试**
   （网络返回异常 ≠ 平台没发布成功，防重复笔记）。先做"发布结果确认"，再定重试策略。
5. **选择器维护体系**：发布页/私信页/主页等 selector 从业务代码抽离，
   集中到配置模块（config/selectors.json 已有，继续收敛残留硬编码）。
   改版只改 selector 层。
6. **平台兼容性自检**：一键检查 Chromium、登录态、创作中心、标题框、
   正文区、上传区、发布按钮、私信入口。改版后直接报"发布按钮 selector 失效"，
   不等到真发布才发现。（发布页/消息页自检已有，合并为统一入口）
7. **线索 CRM 化**：客户来源、账号、昵称、联系方式、最近对话、关键词、
   意向等级、备注、跟进状态、下次跟进时间。从"扫到微信"升级成获客 CRM。
8. **内容矩阵差异化**：母稿 → N 个账号版本（不同标题/开头/正文表达/话题/
   发布时间），记录每个版本实际用了什么。价值不在"一篇发 50 号"，
   在"一个母稿 50 种差异化表达"。
9. **数据闭环**：账号发布量、成功率、线索数、联系方式数、私信数、
   每账号线索产出。总览首页要能回答：哪个账号有价值、哪个失效、
   今天多少线索、哪里出了问题。

## v3.0 · AI 销售助手（远期）

- AI 先做辅助判断，不做全自动回复：识别"价格咨询 / 地址咨询 / 想合作 /
  无效聊天 / 高意向客户"，推荐一条回复，人工确认发送。
- 内容矩阵生成、数据分析、更强的自动化。

## 明确不做的（长期）

- 接码批量注册、全自动无人值守发布
- 自动群发私信 / 自动回复机器人 / 自动评论点赞关注
- 直播间截流、私信截流
- 盲目给"点击发布"加自动重试（防重复笔记）
- 20～50 个长期在线账号之前，不做复杂 CPU/RAM 大盘
- 单机桌面阶段不换数据库（SQLite + 独立连接 + WAL 够用；
  多人协作/远程服务器/多机才考虑 PostgreSQL/MySQL）
